# Human Project intervention and review

Lead and active Seat Agents can publish `artifacts/`, `context/`, or `decisions.md` from their bound Session Workspace as immutable Project working asset versions. Publication requires the current Project revision, the previous SHA-256 for an existing path, and an idempotency key. The retained bytes remain readable by authorized Project members after the source file changes; a released Seat loses access. When the lead submits a final claim, an `artifact_refs` path uses its latest published version if one exists, allowing a Seat's artifact to enter the claim without copying it to the lead Workspace. The recovery bundle verifies every published version's bytes.

Delivery feedback references the exact SHA-256 of a published working asset or the current submitted claim artifact, and retains the reviewed bytes. A lead or active Seat Agent can comment through `bizagent_project_delivery_feedback`; the lead Agent resolves an opinion with a reason and a published working version through `bizagent_project_delivery_feedback_resolve`. The opinion persists before its stable lead Home Inbox notice is attempted. Startup and periodic scans repair missing notices; resolved opinions and closed Projects no longer wake the coordinator. The recovery bundle verifies feedback source and notice provenance.

`registerProjectDeliveryFeedbackRoute` is an optional Host route at `/api/bizagent/project-delivery-feedback`. The Host supplies human authentication, mutation protection and a grant against the current Project. GET lists published and submitted versions with opinions, or downloads a referenced retained snapshot. POST takes the current Project revision, asset SHA-256, version, path, idempotency key and opinion. The Service repeats the Host grant under the Project write lock; the actor comes from the authenticated Host principal. The Projects panel shows this section only when the route grants access. A submitted or accepted claim remains immutable while opinions are handled through working asset versions and the existing review/rework flow.

The Project lead Agent can submit a versioned claim with an assessment against the completion criteria and retained file or formal Work evidence. The Agent may request rework, but cannot accept its own Project claim. Final acceptance goes through `reviewProjectAsHuman`, which checks the current claim, settled Work, Workflow approvals and retained file bytes and records the verified Host principal. Agent rework decisions record their Session ID. Exactly one reviewer identity is allowed per review.

`registerProjectReviewRoute` is an optional Host route at `/api/bizagent/project-review`. The Host must authenticate the human, protect writes against cross-origin mutation, and authorize review against the **current** Project and its lead Home. The body cannot supply an actor or grant. POST requires the current Project revision, claim ID, decision (`accept` or `rework`) and a reason. The Service checks the Host authorization callback again inside the Project write lock. A stale revision or stale claim cannot overwrite a newer result.

For local single-user DSH, the bundled [Bearer-token Host adapter](local-human-host.md) supplies this route when its token file and human ID are configured. It grants review only when the current lead Home's `owner` matches that ID.

An authorized GET returns whether the current claim awaits review. GET with `claimId` and `artifactPath` downloads only a file named in that Project claim. The route rechecks the current Project grant and the retained snapshot's size and SHA-256, and serves it as an attachment. The Projects panel shows the claim body, assessment, Work references and artifact identifiers; authorized reviewers get the file links and acceptance controls. A Host that does not install the route gets the read-only Project panel.

GET `?inbox=1&offset=0` on the same route lists up to 20 current pending claims for the authenticated human. Each item is filtered through the Host's current Project and lead Home grant and includes the exact claim, completion criteria, assessment, Work result text and retained artifact manifests. The **My review queue** in Projects can present these claims without a selected Session Home. A Work artifact download requires the current claim's exact Work ID and result message and rechecks the Project grant before reading the frozen Work snapshot. Acceptance also verifies every referenced Work record and its retained artifact bytes. Decisions still pass through the exact claim route and repeat authorization, revision and evidence checks. The next offset is returned only when more authorized claims exist.

`registerProjectNodeReviewRoute` is a second optional Host route at `/api/bizagent/project-node-review`. It uses the same Host authentication and mutation protection. Its grant callback receives the current Project, node ID and assigned reviewer Home. GET returns the current Project revision and pending Work ID only to an authorized reviewer; an exact `workId` and `artifactPath` downloads a SHA-256 checked Work snapshot while that Work still awaits review. The Projects panel shows the node criteria, result, evidence and approve/rework controls to that reviewer. POST requires the current revision, node and Work IDs, decision and reason; the Service rechecks the current grant inside the write lock and uses the Agent path's latest-result, pause and artifact validation. Node history records exactly one of the verified human principal or Agent Session.

GET `?inbox=1&offset=0` on that route lists up to 20 current pending node reviews for the authenticated human, with an authorized offset for the next page. The Service filters out paused and settled Projects, superseded Work attempts, assignments to another person, and nodes without the Host's current reviewer grant. It returns the exact Work result and artifact manifest, not the whole Project. The Projects view exposes **My reviews** independently of the selected Session Home; a decision and artifact download still use the exact node route and repeat all authorization checks. Without the optional Host route, this entry is hidden.

`registerProjectInterventionRoute` optionally exposes `/api/bizagent/project-intervention` to a human authorized against the current Project and lead Home. POST `pause` requires the Project revision and reason. The Service persists the execution fence before cancelling unsettled Work and sending cancellation notices. The Host's required `afterPause` callback then interrupts known Project Sessions and releases Work runner handles. A callback failure, a reported failed interruption, or an error after the durable fence leaves the Project paused and returns `pause-incomplete`; repeating the same pause retries cleanup. `createProjectInterventionRuntimeHooks` supplies `afterPause` and `inspectRuntime` using the DSH Agent registry, Session query engine and Work runner. The recovery pass also handles pauses left midway through Work cancellation. The audit records either the verified human principal or Agent Session, including on cancelled Work.

POST `resume` requires the current Project revision. The Service rejects unsettled Work, undelivered cancellation notices, and a runtime inspection of `busy` or `unknown`. The Host must supply `inspectRuntime`; a human HTTP request has no coordinator Agent Session to exclude. The Projects panel presents pause and resume only after an authorized access check. A Host without this route gets the read-only intervention state.

For a DSH Host, pass `...createProjectInterventionRuntimeHooks(ctx.agents, ctx.sessionQuery, service, workRunner)` alongside `authenticateUser`, `authorizeMutation` and `authorizeIntervention` when registering the route. The Host should report any `failed` interruption; the route keeps the pause for retry. Never return `quiet` for a Session that cannot be inspected.

`registerProjectPlanRoute` optionally exposes `/api/bizagent/project-plan` for a human authorized against the current Project and lead Home. GET reports the current Project and Workflow revisions and whether amendment, paused rebuild, node redo, or pending reviewer reassignment is eligible. POST `amend` changes the summary and undispatched nodes in place; already dispatched node definitions remain frozen. POST `rebuild` requires a paused Project and a Host `inspectRuntime` callback. It checks settled Work, delivered cancellation notices, quiet Sessions and retained artifacts, then records the new execution epoch and keeps the Project paused until a separate resume. POST `reopen` records the exact completed Work of the chosen node and affected descendants, and refuses active downstream Work. All writes check the current grant inside the Project lock and require the current Project revision; amendments also require the Workflow revision and an idempotency key. Workflow amendment and node redo history record exactly one verified human principal or Agent Session. The Projects panel exposes the editor and redo controls only after an authorized access check.

POST `progression` lets an authorized human manager choose `automatic` or `reviewed` progression with a reason and current Project revision. Reviewed mode supplies an exact reviewer Home for every unfinished Workflow node. The Host must install `authorizeReviewerHome` to expose this control; the Service rechecks every Home's active state and Host grant inside the Project write lock. The change is audited without rewriting the Workflow or Work. When a worker reserves a result, that Work freezes the current progression revision, reviewer Home and criteria (or an automatic gate). Later changes affect future submissions, including Work already running, while pending reviews retain their original gate. Human inbox, reviewer reassignment, artifact access, node status and downstream dispatch use the frozen gate. Legacy Work without a gate keeps its original Workflow reviewer behavior. Recovery validation binds gates and decisions back to the Project progression history.

Each confirmed progression revision also creates one stable, urgent Inbox message for the Project lead Home. The route response includes `notification: delivered` when the Inbox write succeeds or `notification: pending` when it fails after the Project change was saved. The plugin rescans Project history on startup and every Inbox delivery tick, repairs missing messages or receipts, and wakes the lead Home through the Inbox runner. A pending notice does not roll back the manager's decision. The lead Home needs an explicit owner and a configured Workspace mapping to start an automatic wake.

An approved or rework node decision follows the same recovery rule. Its stable Inbox ID is derived from the Project and reviewed Work, and the notice includes the exact node, Work, decision and reason. The lead Home can continue ready nodes after approval or dispatch a new attempt after rework. A failed Inbox write leaves the review intact; startup and periodic scans repair its message or delivery receipt. These Project notices have their own Inbox kinds and do not enter ordinary conversation nudge or convergence rules.

When the manager sends a final Project claim back for rework, one stable notice keyed by Project and claim reaches the lead Home. It includes the exact claim, completion standard and review reason so the coordinator can submit a new version. Acceptance closes the Project without a continuation notice. A failed rework notice keeps the review saved and is repaired by the same startup and periodic Inbox scan.

Recovery scans consider only the current open Project decision. A newer progression revision, a later node decision, a reopened node, a new final claim, or an accepted Project makes an older notice ineligible for automatic wake. A wake plan already reserved for a superseded Project notice is closed without starting a Session.

The lead Agent may call `bizagent_project_plan_propose` with both current revisions, a reason, an idempotency key and a complete draft. The proposal records its Agent Session, base Workflow revision and execution epoch, increments only the Project revision, and leaves the executable Workflow unchanged. The latest proposal is preloaded in the authorized human plan editor while its base revision and epoch still match. A human can edit it or return to the current plan. Saving passes the proposal key through the usual `amend` or paused `rebuild` route; the Service verifies that it is still the latest applicable proposal and records that source in the formal amendment. Agent direct amendment and rebuild tools remain available to the lead Home.

When a human judgment or human-only material blocks the lead, `bizagent_project_request_human` records one question and pauses Project autonomy. It sends the question to the authenticated Human Inbox of an explicit `user:` recipient, the lead Home's owner, or the confirmed principal of an active Role Seat. When another person is the primary recipient, the lead Home's owner receives a copy and may answer if the primary recipient is unavailable. Decision questions may provide two to six suggested answers; either person may write a different reply. A missing notice is retried from the Project ledger. Other Project notices cannot automatically wake the lead while the Project is blocked. `bizagent_project_resume_autonomy` verifies the exact delivered reply from either recipient and records the actual responder, answer, and resuming Agent Session. It leaves an independent execution pause in place for normal inspection and resume.

The reply proves the responder's identity and words. A person-specific or external approval still needs authorization evidence from the host system.

For pending reviewer reassignment, the Host must provide `listReviewerCandidates` and `authorizeReviewerTarget` to the plan route. The list callback supplies eligible human IDs and display names for the node's reviewer Home; the target callback rechecks the chosen person's current grant within the Project write lock. GET with `nodeId` lists candidates only for an authorized Project manager. POST `reassign` requires the current Project revision, exact waiting Work ID, expected current assignee (or `null` for the first assignment), chosen human and reason. Assignment history records the manager, reviewer Home, old and new human, exact Work, reason and time. The assigned person alone may read and decide that pending review through the human route; the reviewer Home's Agent can no longer decide it. Further reassignment leaves the frozen Workflow unchanged. A later Work attempt has its own reviewer assignment.

Project Role Seat ownership is separate from the reviewer assignment above. A lead or active Seat Agent may call `bizagent_project_role_suggest` for an active Role Seat and a human principal registered in the Home directory. The suggestion grants no access. `registerProjectRoleAssignmentRoute` optionally exposes `/api/bizagent/project-role-assignments` to a verified human. The Host supplies Project read and manager grants, CSRF protection, a scoped candidate list, and a target grant checked again inside the Project write lock. A manager can confirm or reject a pending suggestion, assign a candidate directly, or clear a binding with current Project and binding revisions. The Project retains immutable suggestion and decision events; a later role change or released Seat supersedes pending suggestions. The Projects panel shows bindings and pending suggestions when the route is available. A binding describes accountability and does not modify Home owner, Seat access, Work reviewer, or authorization.

These routes do not infer a human owner from an Agent Session. Access responses describe current eligibility; every mutation repeats authorization and settlement checks. Host identity, grants, CSRF policy, runtime hooks and actual business acceptance remain deployment responsibilities. Production Host integration remains open.
