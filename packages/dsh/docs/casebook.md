# 案例指南：把经验放到合适的 Home

以下三个案例使用虚构数据，目的是展示工作流程，不代表客户部署、真实业务政策或已经测得的收益。
每个案例都可运行[同一学习实验](../examples/README.md)，验证从候选到发布、提案、后续使用与退休的规则。

## 案例一：增长分析团队复用留存比较方法

**场景。** 分析 Agent 发现某次活动的总体留存变化混入了获客渠道占比的变化。一次分析中的发现先归
`personal:analyst`，可供岗位长期复用的方法由 `role:growth-strategy` 维护。

**输入。** 当前任务的渠道、注册 cohort、观察窗口与比较结果，以及用户对错误归因的纠正。使用真实数据时，
应明确 cohort 定义、缺失字段和样本范围；教学脚本仅提供合成的用户事件。

**工作步骤。**

1. 在 Personal Home 保存 candidate Method：“比较留存前，对齐渠道与观察窗口”。
2. 读取正文与证据，补充“分别报告分组规模与总体结果，不能单独推出因果结论”的范围限制。
3. 审阅最新 revision 并发布；旧 revision 的发布请求应被拒绝。
4. 向 Role Home 提交完整提案，由 Role owner 检查是否适用于后续分析，再接受。
5. 后续 Role Session 先检索并读方法，使用后记录结果；遇到字段缺失导致误判时，记录反例并复核。

**预期结果。** 发布前，默认搜索看不到候选。提案未接受前，Role 没有新资产。接受后，新的 Role Session
获得一行方法索引，正文按需读取；两次负向结果返回复核信号，owner 可退休该方法。

**注意边界。** BizAgent 不会替你查询数据仓库，也不会自动识别统计混杂。知识内容与业务判断仍由实际任务
和审核提供。原作者的副本不会因 Role 退休而自动失效。

运行：`npm run examples -- growth`。可给真实 DSH Agent 的任务示例：

```text
先确认当前 Home。检查这次分析的渠道与 cohort 定义；把尚未核验的比较方法保存为 candidate，
不要从整体留存变化直接下因果结论。读取正文和证据核验后，再按所审阅的 revision 发布。
若方法值得交给增长岗位复用，向 role:growth-strategy 提案，并说明适用范围和已知例外。
```

## 案例二：研发团队积累配置审查方法

**场景。** 一次配置编辑暴露出“存在备份，但备份无法恢复”的问题。`personal:developer` 记录观察，
`capability:config-review` 维护多个岗位都能使用的审查方法。

**输入。** 实际变更说明、备份校验结果、隔离恢复结果和失败原因。教学脚本描述文件配置，不执行系统修改，
也不连接远程机器。

**工作步骤。**

1. 保存候选，区分“创建备份”与“验证可恢复”。
2. 在正文加入可执行检查：版本化保存、在隔离目录恢复、比较内容、再修改原文件。
3. 明确适用范围是该演示的文件配置，不扩展为数据库迁移通则。
4. 向 Capability 提案，由能力 owner 审阅步骤与证据。
5. 后续使用发现生成文件不在备份中时，记录反例并退休不再适用的版本。

**预期结果。** 能力 Home 得到可按需检索的方法，原始事件可从资产来源追查。相同提案重复接受不会生成
第二份资产；退休后的目标资产保留正文与历史状态，但退出默认索引。

**注意边界。** 存入 Method 不会授权 Agent 执行方法中的所有操作。实际运行仍受用户授权、宿主权限和
项目约束限制。BizAgent 不负责备份系统本身。

运行：`npm run examples -- engineering`。真实任务提示示例：

```text
根据这次配置变更的实际结果，整理可恢复性检查方法，注明配置类型与不适用情形。
先以 candidate 保存；核验原始检查结果后发布，再向 capability:config-review 提交供审核的方法。
```

## 案例三：客服团队维护有范围的业务知识

**场景。** 演示商店中，未发货订单与已发货订单有不同取消流程。`personal:support-agent` 发现容易混淆的点，
`business:demo-store` 负责共同业务知识。

**输入。** 已确认的产品流程版本、订单状态、用户问题与处理结果。示例 policy v1 / v2 均是虚构规则，不能作为
真实退款或取消政策使用。

**工作步骤。**

1. 将候选保存为 Knowledge，而不是把一次客服回复当作普遍适用的方法。
2. 正文写清产品、版本和订单状态；区分应用内取消与需要人工审核的情况。
3. 向 Business Home 提案，由业务 owner 审阅后形成 active 知识。
4. 新会话读取知识再答复，并记录使用结果。
5. 后续政策对部分发货订单发生变化时，记录冲突，核验后修订或退休旧条目。

**预期结果。** 共同知识有明确的维护者与证据来源。发生规则变化时，可保留旧条目用于追查，而不会继续在
默认检索中把它当作当前政策。

**注意边界。** 示例没有爬取帮助中心、自动同步政策或接入工单系统。实际接入前应提供当前有效来源，避免把
一个客户的例外处理写成全体客户规则。

运行：`npm run examples -- support`。真实任务提示示例：

```text
核对当前有效的产品流程，按订单状态整理取消流程的候选 Knowledge，并注明版本、来源与例外。
交给 business:demo-store 审核。只在当前证据支持的范围内回答，不把单个订单的例外推广为共同政策。
```

## 如何增加你自己的案例

从一个容易重复犯错的业务决策开始。定义来源 Home、长期 owner、证据、候选正文、审核条件，以及一条可以推翻
或限制结论的后续结果。把数据添加到 [scenarios.mjs](../examples/scenarios.mjs)，公共 runner 会检查相同生命周期。

若新案例有不同规则，不应只更换故事：增加相应断言，说明与既有案例的差异。贡献流程见仓库根目录
[CONTRIBUTING.md](../../../CONTRIBUTING.md)。
